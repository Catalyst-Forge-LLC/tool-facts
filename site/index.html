Why it exists

MCP annotations exist. Almost nobody sets them, and hosts are told not to trust them.

AppFacts labels the body. ModelFacts labels the brain. ToolFacts labels the toolbelt: what each instrument touches when invoked, in a file you can validate, diff, and wire into policy.

The headline: after a human reviews a label and the host accepts it as evidence, a harness can consume that record as policy input. Example: treat tools marked side_effects: none or read when idempotent is true as candidates for a lighter prompt, gate write, and always prompt on destructive. A schema-valid file is not permission. An unreviewed third-party label does not authorize auto-approval. Read-only is not universally safe. A local scoped read is not the same as unrestricted network read.

The golden rule: if it's subjective ("powerful search tool") it doesn't belong here. If it's objective ("reads files under the workspace root, no network access") it does. When a fact isn't public, the file says undisclosed.

  • Hosts and harnesses that need a policy surface for MCP tools
  • Teams reviewing which servers can write disk or open the network
  • Agent builders composing TOOL_FACTS.md into AGENT_FACTS.md
  • Anyone who wants MCP annotation intent in a file they can CI-check

The format

Frontmatter you can validate. A label you can skim.

---
tool_facts_version: "0.1.0"
name: ForgeTrail MCP Server
developer: Catalyst Forge
version: 0.3.10
status: active
license: Apache-2.0
kind: mcp-server
runtime:
  execution: local-process
  transport: stdio
credentials:
  required: []
egress:
  telemetry: none
  destinations: []
tools:
  - name: runAudit
    purpose: Return a structured audit prompt (does not scan the workspace)
    side_effects: none
    reach:
      filesystem: none
      network: none
      processes: false
    idempotent: true
generated:
  date: 2026-09-16
  generator: hand-authored
---

Spec document 0.1.2. Files declare tool_facts_version (0.1.0 today) so tooling can evolve with them. v0.1 ships mcp-server only. This excerpt is forgetrail-mcp 0.3.10, reviewed 2026-09-16 from that package's tools inventory.

runAudit returns a structured audit prompt. It does not perform the audit or read the project tree. Server-level worst read is validateTracking, a scoped tracking-file check.

A label is bound to a server version and a review date. This site does not run a live drift monitor. Comparing tools/list can show added, removed, or renamed tools. It cannot prove that a same-named tool still does what the label says.

Validate one

Hand-author from the template. Start from MCP tools/list, then classify reach and side effects. The validator is the CI gate. A generator is optional. 

# validate any TOOL_FACTS.md (CI-friendly exit codes)
cd tool-facts/validator && pnpm install
pnpm validate ../examples/forgetrail-mcp/TOOL_FACTS.md
pnpm validate ../examples/*/TOOL_FACTS.md

Frontmatter is checked against tool-facts.schema.json (draft-07). Prefer the harsher side_effects value when unsure. Human-review the file before a host consumes it as policy input. Validation checks schema shape. It does not certify behavior.
